`php artisan formbraid:init` creates config and frontend scaffolds without overwriting existing files. To publish config alone, use `php artisan vendor:publish --tag=formbraid-config`. Laravel discovers the Composer service provider automatically.

## Paths and discovery

```php title="config/formbraid.php"
return [
    'requests' => ['app/Http/Requests', 'app/Modules/**/Requests/**/*.php'],
    'metadata' => 'resources/js/formbraid/_metadata.json',
    'output' => 'resources/js/formbraid/laravel',
    'component_enum' => 'app/Formbraid/FormField.php',
    'submission_driver' => Formbraid\Laravel\Drivers\Fetch::class,
    'fields' => [
        'types' => [
            'string' => 'TextField',
            'boolean' => 'CheckboxField',
        ],
        'rules' => [],
        'fallbackType' => 'string',
    ],
];
```

Paths are relative to the Laravel application. `requests` accepts directories and PHP glob patterns, including `app/Modules/**/Requests/**/*.php`. The default discovery directory is `app/Http/Requests`; the example adds modular requests. The full default mappings include numbers, dates, enums, and files; register only controls your frontend provides.

`metadata` is the JSON snapshot produced by Vite. `output` is the generated TypeScript directory. `component_enum` is a PHP **output file path**, not a class name or an array of separate enum targets. When changing paths, keep the build-only `laravel.ts` registry/metadata URLs, watch patterns, and output exclusions in sync. Init places frontend files in the directory containing `metadata`.

## Bootstrap the merged enum

Keep initial field mappings as strings. Laravel must be able to boot before any generated enum exists; generation does not pre-evaluate config to create it first.

After Vite's first metadata pass, PHP emits one string-backed enum containing field components, form components, and groups. The namespace follows the application's Composer PSR-4 mapping: the default path typically becomes `App\Formbraid\FormField`.

You can then use `FormField::TextField` in `fields()` and `FormField::AddressAutocomplete` in `groups()`, or replace config mappings with generated cases. There is no separate `FormComponent` or `FormGroup` enum to configure. Keep generated output untouched; hash ownership protects it from silent overwrites.

Clear cached config after changing discovery, mappings, paths, or submission generation:

```sh
php artisan config:clear
```

## Submission code generator

Use `Formbraid\Laravel\Drivers\Fetch::class` for self-contained Fetch callbacks, or `Formbraid\Laravel\Drivers\Inertia::class` in an existing Inertia React application. Both emit callbacks into descriptors; neither creates runtime named bindings. Inertia dynamically imports the application's router, with no Formbraid adapter installation or manual CSRF token setup.

A custom class implementing `Formbraid\Laravel\Contracts\SubmissionDriver` can be resolved through the Laravel container. Its `generate(string $endpoint, string $method): string` method receives a safe TypeScript endpoint expression and returns a callback expression. See [producer integrations](../advanced/drivers.mdx).

## PHP inspection boundaries

`formbraid:export` extracts portable schemas and diagnostics; `formbraid:http` inspects HTTP operations. These are lower-level PHP commands, not Node integrations or alternate metadata producers. `formbraid:generate` consumes existing metadata; if absent, start Vite once.

Extraction does not run authorization or validation. Rules must be describable without live authenticated/request state. Keep access control in the actual request lifecycle. See [field mappings](./rules.mdx) and [generation](./generation.mdx).
